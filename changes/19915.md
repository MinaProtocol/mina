Fix zkApps losing their post-hard-fork upgrade path after any account update

After a hard fork, a zkApp whose verification key predates the fork can still be updated with a signature where its permissions would otherwise demand a proof, so that its owner can install a new key. Previously, any update to the account, including one by a third party that did not touch the key, ended this fallback while the old key was still in place, which could leave the zkApp impossible to upgrade. The fallback now lasts until a new verification key is set. GraphQL exposes the version a key was set at as `txnVersion` on the verification key, and transactions are no longer rejected for carrying a different transaction version in their `setVerificationKey` permission.
